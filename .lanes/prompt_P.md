# Workstream: prozorro (directory `prozorro/`, disk budget 4 GB)

Goal: the only large procurement system that publishes every bidder's identity and price is Ukraine's Prozorro. Use it to test whether slip can be forecast per competing bidder, including the price signal a losing bid carries.

## Verified API facts (main session, 2026-09-15 and 2026-09-16)
- Listing: `GET https://public-api.prozorro.gov.ua/api/2.5/tenders?offset=<ISO datetime>&limit=500&opt_fields=status,procurementMethodType,dateModified` returns `data[]` with id, dateModified and the requested fields, plus `next_page.offset` / `next_page.uri`. Offsets are dateModified based. The feed is huge (mostly below-threshold and direct "reporting" procedures); filter client-side on the opt_fields before fetching full tenders.
- Tender: `GET /api/2.5/tenders/{id}` returns `data` with status, procurementMethodType (e.g. aboveThreshold, aboveThresholdUA, aboveThresholdEU, belowThreshold, reporting), value.amount, tenderPeriod, awardPeriod, lots[], items[] (with classification CPV), procuringEntity, bids[] (each with status, date, tenderers[] with name and identifier, value.amount for single-lot tenders or lotValues[] with value.amount and status per lot), awards[] (status, value.amount, bid_id, suppliers), contracts[] (id, status, value.amount, dateSigned, period{startDate,endDate}, awardID, suppliers).
- Contract registry: `GET /api/2.5/contracts/{id}` returns period{startDate,endDate}, value, amountPaid, status, dateSigned, dateModified, contractChangeRationaleTypes, milestones, and changes[] each with rationaleTypes (the vocabulary includes durationExtension, itemPriceVariation, volumeCuts, priceReduction, qualityImprovement, taxRate, thirdParty, fiscalYearExtension; confirm the values you actually observe and count them), status and date. Observed example: tender 6fffbf33eb8d4c908ce7578be33e15a6 (aboveThreshold, expected 66,353 UAH, three bids 49,999.9 / 50,000 / 65,665, award 49,999.9, contract 59,999.88 signed 2024-02-29 with period 2024-02-29 to 2024-12-31 and no changes).
- Be polite: at most 4 concurrent requests, exponential backoff on 429 and 5xx, a User-Agent header, and log request counts. Cache every JSON response under `data/raw/prozorro/` so a rerun does not refetch.

## Tables
- tenders: id, method, buyer id and name, region, CPV division (first 2 digits) and group (first 3), expected value, currency, number of lots, number of bids, tender start and award dates, invasion flag.
- bids: tender id, lot id, bidder identifier and name, bid amount (from value or lotValues), bid status, rank by amount within lot, discount = 1 minus bid over expected lot value, whether this bidder won the lot.
- contracts: tender id, contract id, supplier id, value at signing (tender.contracts[].value), current value (registry), amountPaid, signed date, initial period end (tender.contracts[].period.endDate at signing if the tender copy preserves it; compare with registry period.endDate and report how often they differ), current period end, status, number of changes, change rationale types, duration_extension flag, days_extended = current end minus initial end, value_change_ratio.
Leakage note: the tender document is fetched once in its current state; if bids or contracts in the tender copy are updated after signing, say so and use the earliest evidence you can find (contract `dateSigned`, change `date`).

## Labels (per winning contract)

## Experiments
1. Forecast the winner's duration extension and days_extended > 90 from award-time features: tender method, CPV division, region, log expected value, number of bids, whether the winner was the lowest bid, winner's discount, dispersion of bids (coefficient of variation), buyer history (prior extension rate as of tender date), bidder history (prior tenders won, prior extension rate as of tender date, prior bids submitted). Forward-chained: train on tenders starting 2019 to 2020, test 2021 to 2022 (and 2021 only, excluding post-invasion). Ladder: base rate; CPV x region cell means; GBM without bidder history; GBM with bidder history. Brier, BSS, AUC, calibration.
2. The competing-bidder test. For every bidder in every test tender, compute the forecast extension probability under the with-history model as if that bidder had won (its own history, its own bid discount). Then score bidder-level forecasts by transfer: each bidder's forecasts on lots it lost are compared with its realised extension rate on lots it won in the same test period and CPV division (bidders with at least 3 wins). Report the Spearman correlation between the mean lost-lot forecast and the realised won-lot extension rate, with a permutation null shuffling bidder identity within CPV division.
3. Lowest bidder disqualified: tenders where the lowest bid was disqualified and the next bid won versus tenders where the lowest bid won, matched on CPV division and year. Compare extension and value-change rates. Also the simple relationship between winner discount deciles and extension rate.
4. Does bid dispersion within a tender predict the winner's extension? Binned table.
